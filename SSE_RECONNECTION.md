# Повторное подключение к SSE по request_id

Все POST `*/chat/stream` (включая `/3d`, `/custom` и deprecated-алиасы)
в BuildPlanner, GenPlanner, GenBuilder и PzzCompareAPI поддерживают один контракт.
В BuildPlanner он действует также для `*/run/stream`.
У обычных PZZ-потоков классификации остаётся существующее восстановление по `external_id` задачи.

## Клиентский контракт

1. До первого запроса создайте UUID и сохраните его вместе с текущим ходом чата.
   Передайте `?request_id=<uuid>` или `X-Request-ID: <uuid>`.
   Также поддерживается поле `request_id` в JSON или multipart/form-data.
   Если id не задан, сервер создаст его сам.
2. Первый SSE — `event: pipeline_started`,
   `data: {"type":"pipeline_started","content":{"request_id":"..."}}`.
   Id также возвращается в заголовке `X-Request-ID` (доступном через CORS).
   Все события имеют возрастающий SSE `id`, начиная с 1.
3. После обновления страницы подключитесь с `Authorization: Bearer ...`:

   | Сервис | GET восстановления (относительно корня API сервиса) |
   |---|---|
   | BuildPlanner | `/buildplanner/requests/{request_id}/stream` |
   | GenPlanner | `/genplanner/requests/{request_id}/stream` |
   | GenBuilder | `/requests/{request_id}/stream` |
   | PzzCompareAPI | `/requests/{request_id}/stream` |

   Можно также повторить POST на исходный URL с тем же `request_id`.
   Для существующего запуска тело, обязательные поля и файлы заново не нужны:
   endpoint не вызывается повторно, новый чат/LLM-вызов/генерация не создаются.
4. По умолчанию события воспроизводятся с начала, затем клиент получает новые события
   работающего запроса. Для продолжения после последнего **обработанного** события
   передайте `?after=<id>` или `Last-Event-ID: <id>`; query имеет приоритет.
   Если состояние UI потеряно при обновлении, восстанавливайте поток с начала.
   Пустой поток после последнего события завершённого запроса — нормальный результат.

Используйте fetch-клиент для SSE: native EventSource не позволяет передать Bearer.
Не заменяйте `request_id` на `chat_id`: у каждого хода диалога собственный запуск.
Один id относится к одному пользователю и одному исходному URL; для нового хода нужен новый id.
Неизвестный, чужой или истёкший id при GET даёт 404, неверный курсор — 422.
POST с неизвестным/истёкшим id начинает новый запуск и требует обычное тело запроса;
для восстановления используйте GET, чтобы случайно не выполнить операцию повторно.

В GenBuilder/PZZ доступ проверяется штатной аутентификацией и принадлежностью пользователю;
обновлённый токен того же пользователя подходит. Для opaque-токенов используется отпечаток токена.
BuildPlanner/GenPlanner для SSE проверяют токен через `userinfo` настроенного Keycloak
(`KEYCLOAK_URL` + `KEYCLOAK_REALM`). Новый токен того же пользователя восстанавливает
прежний поток. Отклонённый/истёкший токен даёт 401, недоступный Keycloak — 503;
ошибки проверки не приводят к доверию непроверенному JWT `sub`.
В локальной конфигурации без Keycloak журнал привязан к отпечатку **исходного Bearer**:
в таком режиме повторное подключение требует тот же токен.

## Выполнение и хранение

Вычисление отделено от браузерного соединения. Разрыв SSE отключает только подписчика.
События записываются до отправки клиентам. Конкурентные запросы с одним id атомарно
подключаются к одному запуску; первоначальные HTTP-ошибки валидации сохраняют свои статусы.

Журнал — SQLite из стандартной библиотеки, общий для worker-процессов **одного хоста/pod**.
`SSE_REPLAY_DB` задаёт локальный путь; по умолчанию — `<tempdir>/<service>-sse.sqlite3`.
Путь должен быть доступен на запись всем API workers. Не размещайте эту SQLite на NFS
и не масштабируйте API на независимые pods с раздельными журналами без общего внешнего
хранилища событий/маршрутизации запросов. Текущие dev Deployment имеют по одной реплике.
Новые зависимости и инфраструктура не требуются.

`SSE_REPLAY_TTL` — время хранения после последней активности, по умолчанию 900 секунд
(минимум 120). Работающий producer продлевает срок heartbeat каждые 5 секунд.
Лимит одного журнала событий запроса — 64 MiB, число сохранённых запусков — 1000;
истёкшие записи очищаются при новых запусках. При переполнении запрос завершается
`error`/`done`, при исчерпании числа запусков новый запрос получает 503.

Законченные ответы можно воспроизвести после рестарта worker, если файл журнала сохранился.
Сама незавершённая генерация после рестарта не возобновляется: через 60 секунд без heartbeat
поток получает `error` и `done` со статусом `interrupted`. При штатном shutdown фоновые
задачи закрываются до освобождения зависимостей приложения. При удалении pod/tempdir
журнал теряется. Нельзя автоматически повторять такой запуск: он мог уже иметь побочные эффекты.

ChatStorage хранит историю сообщений и не исполняет SSE-диалог. У Facades-3D собственный
HTTP/WebSocket-протокол генерации с явной отменой при отключении; этот SSE-контракт
к нему не применяется. Запущенная через GenBuilder `/generate/chat/stream/3d` операция
покрыта восстановлением SSE GenBuilder.
