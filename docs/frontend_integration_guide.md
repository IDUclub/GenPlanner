# GenPlanner — гайд для фронтенда

Все эндпоинты живут под префиксом `/genplanner` (см. `app/main.py`). Ниже — только
`gen_planner`-роутер (`app/gen_planner/gen_planner_controller.py`).

## Что изменилось (сентябрь 2026)

Всё, кроме последнего пункта, касается только чата (разделы 5 и 5bis) — REST-контракт из
разделов 1–4 не менялся.

1. **`chat_created` больше не приходит мгновенно.** Чат создаётся после ответа модели —
   зато с осмысленным названием, которое придумала модель, вместо позиционного «Чат 89» от
   ChatStorage. Порядок событий прежний (`chat_created` раньше первого `token`), но ждать
   его теперь столько же, сколько первого токена. См. «Название чата».
2. **Свойства фич в `result` переведены на русский и урезаны.** `territory_zone`,
   `territory_zone_name`, `is_generated` больше не приходят — вместо них «Территориальная
   зона», «Сгенерирована», «Идентификатор исходной зоны». Только в чате: REST отдаёт
   прежний технический формат. См. «Свойства фич в `result`».
3. **`error` бывает не только на стадии `llm`.** Если генератор падает неожиданной ошибкой,
   приходит `error` со `stage: "run_generation"`, но поток на этом не обрывается — следом
   всё равно идут `token` и `done`. Раньше такое падение рвало SSE-соединение, и в браузере
   это выглядело как сетевая ошибка без статуса.
4. **Новая стадия warning — `update_draft`** (модель прислала параметры, которые не
   применились): вместо запуска генерации придёт уточняющий вопрос.
5. **Генерация запускается только по явному согласию пользователя.** Модель больше не
   придумывает баланс зон сама: на «сгенерируй зонирование» без названных зон и долей будет
   уточняющий вопрос, а не несколько минут генерации непонятно чего.
6. **В тексте ответов чата нет английских ключей** (`territory_balance` и прочих) и слов
   «поле»/«параметр»/JSON — только человеческие формулировки. Ключи остаются только внутри
   `metadata.draft` в истории.
7. `POST /genplanner/custom/run_func_generation` (REST): неизвестный `profile_id` — например
   `9` — теперь отклоняется как `422` с перечнем доступных id, а не падает с `500`. Плюс эта
   генерация, как и остальные, ретраится до 3 раз при внутренних сбоях генератора.

## Аутентификация

`run_func_generation`, `run_func_generation/only_zones` и `cut_polygons` требуют
`Authorization: Bearer <keycloak access token>` (обычный пользовательский токен, тот же,
что и для Urban API). Без него — `401`.

`zones_list`, `zones_reference`, `default/func_ratio`, `default_matrix` — без авторизации,
их можно дергать сразу при загрузке формы для справочников.

## 1. Справочники — дёргать до формы генерации

### `GET /genplanner/gen_planner/zones_list` → `list[int]`
Список id функциональных зон-профилей (используются в `default/func_ratio`, не в
`territory_balance` напрямую).

### `GET /genplanner/gen_planner/zones_reference` → `list[AvailableZoneSchema]`
Главный справочник для UI: какие id зон вообще можно использовать в `territory_balance` /
`neighbour_pairs` / `forbidden_pairs`.

```json
[
  {"id": 1, "kind": "residential", "name": "жилая", "profile": null},
  {"id": 2, "kind": "recreation", "name": "рекреационная", "profile": null},
  {"id": 3, "kind": "special", "name": "специального назначения", "profile": null},
  {"id": 4, "kind": "industrial", "name": "промышленная", "profile": null},
  {"id": 5, "kind": "agriculture", "name": "сельскохозяйственная", "profile": null},
  {"id": 6, "kind": "transport", "name": "транспортная", "profile": null},
  {"id": 7, "kind": "business", "name": "деловая", "profile": null},
  {"id": 10, "kind": "residential", "name": "...", "profile": "..."}
]
```
id 10–13 — это подпрофили жилой (`kind: residential`), у них у всех одинаковый `kind`, но
разные `id` — если в UI нужно единое "жильё", группируйте по `kind`, а не по `name`.

**Важно:** бэкенд не валидирует id зон в `territory_balance` / `neighbour_pairs` /
`forbidden_pairs` явной 422-ошибкой — неизвестный id молча выбрасывается из расчёта
(в худшем случае — с непонятной ошибкой из недр генератора, если выброшены все id).
Присылайте только id из этого справочника.

### `GET /genplanner/default_matrix` → `{"forbidden_pairs": [[int, int], ...]}`
Дефолтные запрещённые пары **по умолчанию** (используются, если не передавать
`neighbour_pairs`/`forbidden_pairs`/`ignore_default_relations` вовсе). Полезно показать в UI
как preset ("стандартные ограничения соседства"), который пользователь может донастроить.

### `GET /genplanner/default/func_ratio?zone=<id>` → `dict[str, float]`
Дефолтное распределение зон для одного из "профилей" из `zones_list` (id из `zones_list`,
не из `zones_reference`) — годится как стартовое значение слайдеров `territory_balance`,
если пользователь выбрал готовый профиль, а не настраивает баланс вручную.

## 2. Генерация: `POST /genplanner/run_func_generation`

Тело запроса — `GenPlannerFuncZonesDTO` (`app/gen_planner/dto/gen_planner_func_dto.py`):

| поле | тип | обязательное | описание |
|---|---|---|---|
| `project_id` | int | да | |
| `scenario_id` | int | да | |
| `territory_balance` | `dict[int, float]` | да, ≥1 запись | id зоны → доля площади. Id только из `zones_reference` |
| `neighbour_pairs` | `list[[int, int]]` \| null | нет | пары id, которые нужно **поощрять** к соседству |
| `forbidden_pairs` | `list[[int, int]]` \| null | нет | пары id, которые нужно **отговаривать** от соседства |
| `ignore_default_relations` | bool | нет, default `false` | `true` — не применять дефолтные запреты (`default_matrix`), стартовать с чистой матрицы |
| `functional_zones` | объект \| null | нет | режим доработки (amendment) существующих зон, см. ниже |
| `fix_zones` | GeoJSON FeatureCollection \| null | нет | точки/геометрии с явно закреплённым типом зоны |
| `min_block_area` | `dict[int, float]` | нет | переопределение минимальной площади квартала по зоне |
| `elevation_angle` | int (0–90) \| null | нет | обрезка по уклону рельефа |
| `roads_extend_distance` | float \| null | нет, default `5` | |
| `test` | bool | нет, default `false` | тестовая БД вместо боевой |

### Про `neighbour_pairs` / `forbidden_pairs` — как это реально работает

Это **не жёсткое ограничение**, а штраф внутри оптимизатора генератора (подтверждено и
исходниками Rust-ядра, и живыми прогонами: 4 повтора baseline против 4 с
`forbidden_pairs=[[1,2]]` дали границу зон 23–192 м vs 0–2 м — эффект чёткий, но не
гарантированный ноль). Формулировки в UI должны быть аккуратными:

- Хорошо: "снизить вероятность соседства", "постараться развести зоны"
- Плохо: "гарантированно запретить соседство", "зоны никогда не будут рядом"

Обе зоны в паре обязаны присутствовать в `territory_balance` — иначе пара молча
игнорируется на бэкенде (см. предупреждение выше).

### Режим доработки существующих зон — `functional_zones`

```json
{
  "functional_zones": {
    "year": 2025,
    "source": "User",
    "fixed_functional_zones_ids": [1619712]
  }
}
```
- `source`: `"PZZ" | "OSM" | "User"` — откуда брать текущие функциональные зоны сценария.
- `year`: год снепшота.
- `fixed_functional_zones_ids`: опционально — конкретные существующие зоны, которые нужно
  оставить как есть (закрепить), а генератор доразмечает только оставшуюся территорию.
  Если не передавать — используется просто как контекст/база для доработки, без жёсткой
  фиксации конкретных зон.

Если `functional_zones` не передан — генерация "с нуля" по всей территории проекта/сценария.

### Ответ — `GenPlannerResultSchema`

```json
{
  "zones": { "type": "FeatureCollection", "features": [
    {"type": "Feature", "geometry": {...}, "properties": {
      "territory_zone": 1,
      "territory_zone_name": "residential",
      "functional_zone_id": null,
      "is_generated": true
    }}
  ]},
  "roads": { "type": "FeatureCollection", "features": [...] }
}
```
`is_generated: false` — это зона, пришедшая из `fix_zones`/`functional_zones` как есть, без
пересчёта геометрии; `functional_zone_id` заполнен только для таких "перенесённых" зон.

**Если тестировали до 24 июля** — раньше был баг: если в `territory_balance` указан один
из "жилых" подпрофилей (`10`/`11`/`12`/`13`) **и** для него передан кастомный
`min_block_area`, в ответе `territory_zone` у сгенерированных зон этого профиля мог
ошибочно прийти `1` вместо реального id. Исправлено (`5ff0bb0`) — сейчас `territory_zone`
в ответе всегда соответствует id, который был передан в запросе.

### `POST /genplanner/run_func_generation/only_zones`

Тот же DTO, но результат содержит только `functional_zone_id`/`is_generated` (без
`territory_zone_name`) — используйте, если UI не нужны подробности, только сами полигоны +
id. Более компактный ответ, тот же движок.

## 3. Тайминги, ретраи, недетерминизм — критично для UX

- **Не sub-second эндпоинт.** Реальная генерация — от ~60 секунд до нескольких минут
  (особенно если несколько генераций идут параллельно и делят CPU — на бэкенде это
  синхронный CPU-bound расчёт в потоке, не async I/O). UI обязан показывать
  progress/spinner с реалистичным ожиданием, не таймаутить запрос раньше 3-5 минут.
- **Бэкенд сам ретраит** до 3 раз при внутренних сбоях генератора (известны редкие
  паники в Rust-ядре на некоторых геометриях) — если после 3 попыток не получилось,
  клиенту прилетит ошибка; это стоит показывать как "не получилось сгенерировать,
  попробуйте ещё раз", а не как баг конкретно этого запроса.
- **Результат недетерминирован.** Один и тот же запрос с одинаковыми параметрами может
  дать разную планировку при каждом вызове (внутри генератора нет пробрасываемого seed —
  каждый вызов использует случайную инициализацию). Если в UI есть кнопка "перегенерировать"
  с теми же параметрами — это ожидаемо и полезно, а не признак бага.

## 4. Ошибки

Явно провалидированные случаи возвращают `422` с телом вида:
```json
{"msg": "...", "input": {...}, "detail": {...}}
```
Примеры: несуществующие `fixed_functional_zones_ids`, зафиксированные зоны не того типа,
fix-точки вне территории. Показывайте `msg`/`detail` пользователю как есть — там нет
внутренних деталей инфраструктуры.

Неожиданные внутренние ошибки сейчас возвращаются как обычный `500` без подробностей
(глобальный exception-handler в проекте временно отключён) — на такой случай в UI нужен
универсальный fallback "что-то пошло не так", без попытки распарсить `detail`.

## 5. Чат-агент (SSE): `POST /genplanner/scenarios/{scenario_id}/chat/stream`

Диалоговый способ задать те же параметры генерации текстом вместо формы. Требует
`Authorization: Bearer <token>` (тот же токен, что и для REST выше) и заголовок
`Accept: text/event-stream`. `project_id`/`scenario_id` **никогда не берутся из текста
чата** — `scenario_id` из URL, `project_id` резолвится сервером сам.

### Тело запроса — `ChatTurnDTO`

```json
{
  "user_query": "Хочу 50% жильё, 30% бизнес и 20% рекреации",
  "chat_id": null,
  "test": false
}
```
- `user_query` — обязательное, непустое.
- `chat_id` — `null`/не передавать для нового диалога; для продолжения — id, полученный
  из события `chat_created` первого хода (см. ниже).
- `test` — тот же смысл, что и в REST-DTO.

### Что чат умеет задавать, а что нет

- **Напрямую из текста**: `territory_balance`, `neighbour_pairs`, `forbidden_pairs`.
- **Через уточняющий вопрос**: `min_block_area`, `elevation_angle`, `roads_extend_distance`.
- **Никогда не через чат**: `project_id`, `scenario_id` (сессия/URL), `fix_zones`,
  `functional_zones` (нужна карта — вне MVP чата; используйте прямой REST для этих
  режимов).

Зоны в чате называются **словами, а не id**: пользователю не нужно знать номера, а агент
оперирует названиями из `zones_reference` («жилая», «рекреационная», …) и понимает
разговорные синонимы («жильё», «промка», «парк»). В id название превращается уже внутри
бэкенда, поэтому в `metadata.draft` сохранённых сообщений баланс по-прежнему лежит
ключами-id — формат истории не менялся.

Одно ограничение: жилые подпрофили (`10`/`11`/`12`/`13`) через чат недоступны — у них
общее с id `1` название «жилая», и оно всегда резолвится в `1`. Нужен конкретный
подпрофиль — только прямым REST-запросом с id.

### Формат ответа — SSE-события

Каждое SSE-сообщение — `event: <type>` + `data: <JSON>`, тот же объект и в `type` внутри
`data`. Возможные `type`, в порядке появления за один ход:

| `type` | когда | поля |
|---|---|---|
| `chat_created` | только на первом ходе нового диалога, **после ответа модели**, а не сразу при открытии потока | `chat_id`, `title` (название от модели) — сохраните `chat_id` и передавайте в следующих ходах |
| `warning` | см. таблицу `stage` ниже | `stage`, `detail`, `message` (готовый текст для пользователя, есть не всегда — см. ниже) |
| `token` | текст ответа ассистента, нарезанный кусками по ~24 символа | `content` — конкатенируйте по порядку получения, это и есть полный ответ |
| `result` | только если ход завершился реальным запуском генерации | `zones`, `roads` — те же FeatureCollection, что и в `GenPlannerResultSchema` из REST, но с переписанными `properties` (см. «Свойства фич в `result`» ниже) |
| `error` | `stage: "llm"` — LLM-шаг упал целиком (напр. vLLM недоступен); `stage: "run_generation"` — генератор упал неожиданной ошибкой; `stage: "territory"` — только в custom-чате (см. 5bis) | `stage`, `detail`. При `llm`/`territory` дальше сразу `done`, без `token`/`result`; при `run_generation` поток продолжается: придут `token` с объяснением и `done`, но не `result` |
| `done` | всегда последним | `chat_id`, `assistant_message_id` (`null`, если сохранение в историю не удалось) |

Пример полного хода с генерацией:
```
event: chat_created
data: {"type": "chat_created", "chat_id": "abc123", "title": "Зонирование с упором на жильё"}

event: token
data: {"type": "token", "content": "Запускаю генера"}

event: token
data: {"type": "token", "content": "цию с балансом 50/30/20..."}

event: result
data: {"type": "result", "zones": {...}, "roads": {...}}

event: done
data: {"type": "done", "chat_id": "abc123", "assistant_message_id": "msg456"}
```

### Название чата — `chat_created.title`

Название придумывает модель в том же вызове, которым отвечает на первое сообщение: на первом
ходе нового диалога в её JSON-схему добавляется поле `chat_title`. Лишнего похода в LLM нет,
но и чат до ответа модели не создаётся — поэтому `chat_created` приходит с той же задержкой,
что и первый `token` (обычно единицы секунд, а не мгновенно, как раньше). Порядок событий не
изменился: `chat_created` по-прежнему раньше любого `token`.

Что приходит в `title`:
- 2–5 слов по сути запроса, с заглавной буквы, без кавычек и точки в конце, максимум 60
  символов (длиннее — обрезается по границе слова и заканчивается «…»);
- если модель вернула негодное название (приветствие, целое предложение, пустую строку) —
  оно собирается из первого предложения сообщения пользователя;
- если модель не ответила вообще (`error` со `stage: "llm"`) — тоже из сообщения
  пользователя; а если и оно слишком короткое («да», «?») — «Генерация функционального
  зонирования» (в custom-чате — «Зонирование загруженной территории»).

Название пишется в ChatStorage один раз, при создании чата, и в следующих ходах не
обновляется — переименования со стороны бэкенда не будет, в списке истории показывайте
`title` из `chat_created` (или то, что отдаёт ChatStorage).

### Свойства фич в `result` — только русские названия

`result` из чата уходит прямо в слой на карте, а панель атрибутов показывает `properties` как
есть, поэтому в чате (и только в чате) свойства фич переписываются на русский, а числовой id
зоны заменяется её названием. REST-эндпоинты из раздела 2 отдают прежний технический формат —
машиночитаемые ключи там не тронуты.

Было (и остаётся в REST):
```json
{"territory_zone": 2, "territory_zone_name": "recreation", "functional_zone_id": null, "is_generated": true}
```
Стало (в `result` чата):
```json
{"Территориальная зона": "рекреационная", "Сгенерирована": "Да"}
```
- **«Территориальная зона»** — русское название из того же словаря, что и `name` в
  `zones_reference`; если зону распознать не удалось — «не определена». Жилые подпрофили
  (`10`–`13`) здесь неразличимы: все показываются как «жилая».
- **«Сгенерирована»** — «Да»/«Нет» вместо `is_generated`; ключа нет, если поля не было.
- **«Идентификатор исходной зоны»** — бывший `functional_zone_id`, приходит только у зон,
  перенесённых из существующего зонирования.
- Остальные атрибуты, которые тянутся вместе с зонами из Urban API (`year`, `source`,
  `created_at`, …), вырезаны — это whitelist из трёх полей, а не переименование всех подряд.
- У дорог остаются только **«Название»** и **«Адрес»**, и только если они непустые.

Геометрия и структура FeatureCollection не менялись — переписан только `properties`. Если UI
раскрашивает слой по типу зоны, ключом теперь служит русское название, а не `territory_zone`.

### `warning.stage` — какие бывают и что означают для `result`

| `stage` | когда | придёт ли следом `token`/`result` |
|---|---|---|
| `load_history` | не удалось загрузить историю чата из ChatStorage | да, отвечает без учёта истории |
| `create_chat` | не удалось создать чат в ChatStorage | да, просто без сохранения (и без `chat_created`) |
| `add_user_message` | не удалось сохранить сообщение пользователя | да, без сохранения этого сообщения |
| `add_assistant_message` | не удалось сохранить ответ ассистента | `token` уже пришёл раньше этого warning; `result` — если генерация была |
| `update_draft` | модель прислала параметры, которые не прошли валидацию черновика | да — вместо запуска придёт уточняющий вопрос, `result` не придёт |
| `run_generation` | LLM решил запускать генерацию, но `GenPlannerService` отклонил параметры (422-подобная ошибка) | **`token` придёт (с объяснением), `result` — нет** |

Первые четыре стадии — проблемы ChatStorage (инфраструктура истории), они не мешают
сгенерировать ответ/результат в этом ходе. Две последние — другое дело:

- `update_draft` — параметры, которые предложила модель, не применились к черновику;
  `message` заполнен («Не удалось применить выбранные параметры…»), а в `token` придёт
  уточняющий вопрос вместо запуска.
- `run_generation` — сама генерация не запустилась. `detail` здесь — тот же объект
  `{msg, input, detail}`, что и в `422` у REST-эндпоинта, `message` не заполняется (только
  `stage`/`detail`), текст для пользователя берите из следующего `token`-потока. Этот текст
  теперь формулирует бэкенд, а не модель («Генерация не запустилась: …»): ответ модели,
  который уже объявил запуск, заменяется целиком, чтобы пользователь не читал «запускаю
  генерацию» рядом с сообщением об ошибке. То же самое при `error` со
  `stage: "run_generation"` — «Генерация завершилась ошибкой на стороне сервиса…».

### Прочие нюансы

- **503**, если чат не сконфигурирован на бэкенде (`VLLM_BASE_URL`/`CHAT_MODEL` не
  заданы) — отдельного эндпоинта "доступен ли чат" нет, обрабатывайте `503` при первом
  запросе (например, скрыть/задизейблить чат-виджет и показать фолбэк на обычную форму).
- **`warning` — не то же самое, что `error`, но и `error` больше не всегда конец хода.**
  Ход почти всегда доводится до `token`/`done` — см. таблицы выше про то, приходит ли ещё и
  `result`. Для history-стадий показывайте `warning.message` как ненавязчивый тост, не
  блокируйте UI; для `update_draft`/`run_generation` — просто не ждите `result` и полагайтесь
  на текст в `token`. Единственные события, после которых сразу идёт `done`, — `error` со
  `stage: "llm"` и (в custom-чате) `stage: "territory"`.
- **Генерация не стартует без явного согласия пользователя.** Модель обязана дождаться
  и названного пользователем баланса зон, и слов вроде «запускай»/«поехали»; собственные
  догадки она предлагает вопросом. Для UI это значит, что кнопка/подсказка «запустить
  генерацию» полезна, а на первое общее «сделай зонирование» ожидаемо придёт вопрос, а не
  `result`.
- **Персист истории требует, чтобы `sub` в токене был UUID** — для реальных
  пользовательских Keycloak-токенов это так; для синтетических/тестовых токенов с
  нестандартным `sub` сохранение молча не работает (без ошибки, просто следующий `chat_id`
  не будет иметь памяти о предыдущих ходах).
- Живьём проверено 27 июля против реального Ollama (`gpt-oss:20b`) и реального ChatStorage
  — обычный сценарий "дать баланс → подтвердить → получить result" и "дать баланс и сразу
  попросить запустить в одном сообщении" оба работают и сохраняют историю корректно.
- С тех пор LLM-бэкенд переключён на vLLM (`VLLM_BASE_URL`, OpenAI-совместимый
  `/v1/chat/completions`, модель `gpt-oss-20b`); контракт SSE-событий не менялся. Ollama
  остаётся как альтернативный бэкенд — `LLM_PROVIDER=ollama`.

## 5bis. Чат-агент на своей территории (без проекта/сценария): `POST /genplanner/custom/chat/stream`

Тот же диалоговый способ запустить генерацию, но без привязки к проекту/сценарию
платформы — территория задаётся файлом границы, который пользователь загружает сам.
Требует `Authorization: Bearer <token>` и `Accept: text/event-stream`, как и обычный чат
выше, но токен здесь нужен только для идентификации пользователя в ChatStorage — Urban
API не вызывается вообще.

**Важное ограничение**: генерация в этом режиме не учитывает дороги, воду и уклон
рельефа (для них нет источника без сценария) и запускает **один** готовый профиль
зонирования на всю территорию целиком — не произвольный баланс нескольких зон, как в
обычном чате. `fix_zones`/`functional_zones` тоже недоступны.

### Тело запроса — `multipart/form-data`, не JSON

| поле | тип | обязательность |
|---|---|---|
| `user_query` | text | всегда |
| `chat_id` | text | не передавать для нового диалога; иначе — id из `chat_created` первого хода |
| `territory_file` | file | **обязателен на первом сообщении нового диалога** (когда `chat_id` не передан); необязателен на последующих ходах того же `chat_id` — граница уже сохранена в истории первого хода |

Поддерживаемые форматы `territory_file`: GeoJSON (`.geojson`/`.json`), Shapefile в
`.zip` (обычный `.shp`+`.shx`+`.dbf`+`.prj`, зазипованные вместе), KML (`.kml`).
Если у геометрии в файле не задана система координат — она считается WGS84
(EPSG:4326); если задана — переприводится в 4326 автоматически. Лимит размера файла —
15 МБ. Некорректный формат/пустой файл/геометрия не типа Polygon-MultiPolygon —
`400` до старта SSE-потока (обычный JSON `{msg, input, detail}`, не SSE-событие).

Если `chat_id` передан, но границы в истории этого чата ещё нет (не должно происходить
в норме, но на случай рассинхронизации) — при отсутствии `territory_file` в этом ходе
придёт `error` с `stage: "territory"` вместо генерации.

### Что чат умеет задавать, а что нет

- **Напрямую из текста**: профиль зонирования — один, по названию («жилая»,
  «рекреационная», …, «базовая»); список названий — в `GET
  /genplanner/gen_planner/zones_reference` (поле `name`). Id профиля пользователю
  показывать не нужно: чат понимает и разговорные синонимы, а в `profile_id` название
  превращает бэкенд (в `metadata.draft` по-прежнему сохраняется id).
- **Никогда не через чат**: territory (файл, один раз на первом ходе), `territory_balance`
  / `neighbour_pairs` / `forbidden_pairs` / `min_block_area` / `elevation_angle` /
  `roads_extend_distance` (не поддерживаются в custom-режиме вовсе — используйте обычный
  чат/REST со сценарием, если они нужны).

### Формат ответа

Тот же набор SSE-событий (`chat_created`/`token`/`result`/`warning`/`error`/`done`) и та
же семантика `warning.stage`, что и у обычного чата (раздел 5 выше) — стадии `load_history`
/`create_chat`/`add_user_message`/`update_draft`/`add_assistant_message`/`run_generation`
работают одинаково в обоих режимах. Название чата модель придумывает так же (фолбэк —
«Зонирование загруженной территории»), и `properties` в `result` так же переписаны на
русский. Дополнительная стадия только у `error`: `territory` — см. выше.

## 6. MCP-сервер (для ВНЕШНИХ агентов, не для нашего чата и не для обычного UI)

Это отдельный процесс (`app/mcp_server`, порт `8766` по умолчанию) для сторонних
LLM-клиентов (Claude Desktop, другие агенты вне этого продукта), не для нашего
чат-виджета из раздела 5 — тот ходит в `GenPlannerService` напрямую, в обход MCP. Тулы:
`list_available_zones`, `list_zone_types`, `get_func_zone_ratio`,
`get_default_forbidden_matrix`, `run_func_generation`. Для обычного UI-фронтенда и для
чат-виджета это не нужно — используйте REST/SSE-эндпоинты выше напрямую.
